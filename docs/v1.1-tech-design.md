## Overview and goals

v1.1 turns the v1 sine demo into a Beatality demo: a held C1 opens Beatality's gate, an LFO and two sliders move its parameters through control cables, and the page can open in a locked play-only mode. Everything still runs on localhost with the v1 black-on-white look.

Target scene (the new `demo.json`):

- **Note hold** (new plugin) holds one note (C1 by default, any note allowed) while the transport plays → **Beatality** → **Master**. These two cables exist on open.
- **Beatality** appears on the canvas as itself: its own UI inside its node box, with volume and pan on the box. It is dragged by its header like any node.
- **LFO** (new plugin, synced to BPM: one cycle per bar) and **Control sliders** (new plugin, 2 sliders) sit in the scene unconnected. The user draws control cables to any parameter, or to any node's volume or pan.

| # | Feature | Where it lives | Already present? |
| --- | --- | --- | --- |
| 1 | Camera pan: right-mouse drag, two-finger trackpad scroll | ivan-daw `canvas`, `store` | No. Canvas is 1:1 screen pixels, boxes are clamped to the window |
| 2 | Beatality on the canvas with its own UI, volume and pan | Beatality repo (own session, PR + CI release); ivan-daw fetches the release and shows plugin UIs inside node boxes | No. Beatality implements API v1 only; v1 boxes have no plugin UI |
| 3 | Note hold: endless note, any pitch | ivan-daw `plugins/note-hold` | No. `note-gen` plays C3 for half a beat on every beat |
| 4 | Control inputs on volume, pan and every automatable parameter | ivan-daw `model`, `router`, `canvas`, `panels` | No. The `modulation` port kind exists in the API types, but nothing routes it |
| 5 | Basic LFO, synced to BPM | ivan-daw `plugins/lfo` | No in ivan-daw. Beatality's rack has a v1 test LFO to borrow from |
| 6 | Control sliders, 2 sliders | ivan-daw `plugins/control-sliders` | No |
| 7 | Play-only mode at `/play_only` | ivan-daw `app`, `canvas`, `panels`, `engine` (Master pan) | No |

Out of scope: zoom, save / load, undo, hosting, LFO shape or rate controls, hardware Web MIDI input, binding depth or range.

## Current state (read 2026-11-13)

v1 is finished through P11: Play gives C3 on every beat from note-gen into the sine synth. Nothing in v1 carries control values yet, and Beatality is not loadable by the DAW.

| Repo | Default branch | State | What v1.1 touches |
| --- | --- | --- | --- |
| ivan-daw | `main` | P1–P11 merged; plugins `note-gen`, `base-sine-synth`; core pinned by git tag | canvas, model, router, panels, app, 3 new plugins, fetched Beatality |
| ivan-daw-core | `main` | v0.1.0: API v2 types, transport math, MIDI helpers, Envelope / Smoother | small additions, tag v0.2.0 |
| Beatality | `master` | C++ engine → wasm; `apps/web-widget/src/plugin.tsx` is an API v1 plugin with a 746 px Preact UI and about 40 parameters | v2 plugin entry + DAW build + CI release, by PR, in its own session |

Facts that shape the design:

- `PortInfo` already has `kind: 'modulation'`, direction `out` only. The v1 design reserved "one control input per automatable parameter" and decided control travels as `automation` events.
- `Router.validate` handles audio and events only. `compatible()` would accept modulation → modulation, but no plugin declares a modulation input, so no cable can land.
- The canvas clamps every box inside the visible window (`clampToBounds`) and has no camera.

## Architecture

v1.1 keeps the v1 layers (UI → store → engine, scheduler, router → plugins) and adds one new cable kind, control, that the router already knows how to carry: it is an event stream of `automation` values. No plugin talks to another; the router forwards every value along a cable.

```text
Note hold --notes--> Beatality.in            Beatality.out --audio--> Master
LFO.out        ··control··> <any node>.ctl:gain | ctl:pan | ctl:param:<id>
Sliders.a / .b ··control··> <any node>.ctl:...
(all cables go through the router)
```

Control cables are dotted and end on host-made `ctl:*` inputs. Pan and volume are the node's strip, handled by the host; plugin parameters are reached through `schedule()`.

Contract changes:

| Contract | Change | Breaking? |
| --- | --- | --- |
| C1 API types (core `api.ts`) | None. `modulation` out ports, `automation` events, `ui`, `mount` / `unmount` already exist | No |
| C2 transport / core helpers | `NOTE.C1 = 36` in `midi.ts`; core tag `v0.2.0` | No |
| C3 project schema | Cable `to.port` may be `ctl:gain`, `ctl:pan`, `ctl:param:<id>`; format stays `version: 1` | No (old projects still load) |
| C4 store | New `camera` signal, `panCamera()`; new `mode` signal (`edit` \| `play`) | Additive |
| C5 engine | Master gets a pan stage; engine mounts plugin UIs into node boxes | Additive |
| C5 router | `validate` / `plan` resolve `ctl:*`; `Wiring` gets a `control` list; apply ramps strip params | Additive |
| C6 catalog | `plugins/beatality` is fetched, not built | Additive |
| C7 test hook | Adds `mode()` and `camera()` | Additive |

The Plugin API doc gets one paragraph: "Control inputs are made by the host for every automatable parameter and for strip volume and pan; plugins do not declare them."

## Feature designs

### 1. Camera pan

The canvas gets a camera offset; node positions stay in world pixels, so the project format does not change.

- New view signal `camera = signal({ x: 0, y: 0 })` in the store, plus action `panCamera(dx, dy)`. It is view state, not project state, so it is not saved.
- The canvas wraps the node boxes and the SVG cable layer in one `#ivd-world` element with `transform: translate(-camera.x px, -camera.y px)`. Pointer positions convert screen → world with one function, `toWorld(pt, camera)`, used by drag, connect and hit tests.
- Right mouse button: `pointerdown` with `button === 2` anywhere on the canvas starts a pan with pointer capture; `contextmenu` is prevented on the canvas.
- Trackpad: a `wheel` event without `ctrlKey` pans by `(deltaX, deltaY)` (pixel mode; line mode × 16). `ctrlKey` wheel (pinch) is ignored until zoom exists. A mouse wheel also pans vertically, which is fine.
- Node drag no longer clamps to the window. A box only keeps `x, y ≥ −2000` as a sanity limit, so it cannot be lost forever.
- `+ Add` places new nodes at the centre of the current view (`camera + canvas size / 2`).

### 2. Beatality in the DAW

Beatality's own changes are specified in a separate design, "Beatality as an IvanDAW plugin — Technical Design", which goes to the Claude Code session in the Beatality repo. It lands there by PR, and Beatality's CI publishes every `master` build as a GitHub release. This project never changes Beatality.

**Blocker B (Beatality ready):** cleared when the Beatality PR is merged, its CI has published a `daw-build-<n>` release with `beatality-daw.zip`, and the PR has its "Ready for IvanDAW" section. Every IvanDAW task that loads Beatality waits for it. Until then the control-cable work is tested against the base sine synth's `level` parameter.

Taking the build (ivan-daw):

- `plugins/beatality/package.json` holds the plugin id and the pinned release, for example `"ivandaw": { "id": "com.beatality.beatality", "release": "daw-build-42" }`.
- `scripts/fetch-beatality.mjs` downloads that release's `beatality-daw.zip` from GitHub (public repo, no token) and unpacks it into `plugins/beatality/dist/`, which is git-ignored. It skips the download when that release is already there. `pnpm i` and `pnpm dev` run it.
- `pnpm beatality:update` moves the pin to the newest `daw-build-*` release and fetches it. Claude commits the new pin after a localhost check.
- The catalog dev plugin already serves `plugins/<name>/dist`, so nothing else changes in loading.

Plugin UI inside the node box (any plugin whose manifest has `ui`; in v1.1 only Beatality):

- The box grows to `ui.width` × `ui.height` plus a header and a footer. Once the node is `ready`, the engine calls `instance.mount(body)`; before removal it calls `unmount()`.
- The header (name, status dot) is the drag handle. The body belongs to the plugin: its clicks, keys and wheel go to it. Right-drag over the body still pans the camera.
- Footer, on every node with a main audio out (not only Beatality): compact Volume and Pan sliders calling `setGain` / `setPan`, the same as the node panel.
- Ports as on any node: notes in on the left (from Note hold or any midi node), the `ctl` input for control cables, audio out on the right to Master.
- Plugins without `ui` (Note hold, LFO, Control sliders, sine synth) keep the 180 px box.

### 3. Note hold (`com.ivandaw.note-hold`)

A `midi` plugin that holds one note for as long as the transport plays. It is a gate source for Beatality, which plays its loop while any note is held, so the pitch does not matter to it.

| Field | Value |
| --- | --- |
| kind | `midi` |
| ports | `out`: events, out, `midi` |
| parameters | `note`: int 0..127, default 36 (C1), shown as a note name; automatable. Velocity fixed at 100 |

- `transport {playing: true}` at time T → emit note on `[0x90, note, 100]` at T.
- `transport {playing: false}` or CC 123 at time T → emit note off for the held note at T, only if one is held.
- `note` changes while held → note off for the old pitch and note on for the new one, both at the event time.
- A second `playing: true` while already on (BPM change) emits nothing. `dispose` emits the note off if needed.
- No ticker: it reacts only to events, so it cannot drift. `note-gen` stays in the catalog as it is.

### 4. Control inputs (MIDI-controllable parameters)

Every node gets host-made control inputs; plugins do not declare them. A control cable runs from a `modulation` out port to one of them and carries `automation` events.

Control input ids (the `port` of a `PortRef`):

| Port id | Target | Value mapping (control 0..1 →) |
| --- | --- | --- |
| `ctl:gain` | the node's strip volume | 0..1.5 |
| `ctl:pan` | the node's strip pan | −1..1 |
| `ctl:param:<id>` | plugin parameter `<id>`, `automatable: true` only | the parameter's normalized 0..1, unchanged |

- The project format stays `version: 1`; cables simply allow the new port ids. `findPort` resolves `ctl:*` from the node's manifest and `parameters()`.
- A control input takes one cable; a new cable replaces the old one, like any input.
- Canvas: each node shows one dotted `ctl` input at the bottom-left of its box. Dropping a control cable on it opens a small list of that node's control inputs (Volume, Pan, then parameters by `group`). The cable is labelled with the parameter name at its end.
- Router: modulation edges go into the event table. For `ctl:param:<id>` it calls `schedule([{type:'automation', time, id, value, source:'binding'}])`. For `ctl:gain` / `ctl:pan` it ramps the strip AudioParam with `linearRampToValueAtTime(mapped, time + 0.025)`, so the 40 Hz control stream is smooth.
- Node panel: a bound control shows "← <source node>" next to its slider and the slider is disabled. Removing the cable restores the stored value with a 5 ms ramp.
- Validation adds nothing new: rule 3 (same kind) already rejects modulation → events; cycles count control edges too.

### 5. LFO (`com.ivandaw.lfo`)

| Field | Value |
| --- | --- |
| kind | `modulator` |
| ports | `out`: modulation, out |
| parameters | none; one cycle per bar (4 beats) and full 0..1 swing are constants |

- Synced to the transport: `value(beat) = 0.5 − 0.5 · cos(2π · beat / 4)`, where `beat` comes from the transport anchor with `beatAt` from ivandaw-core, the same math note-gen uses. A BPM change keeps the phase and changes the speed; Stop returns it to beat 0.
- While playing: `createTicker(25)`; each tick emits one `automation` event `{id: 'out', value: value(beatAt(t)), time: t}` with `t = now + 0.025`.
- While paused or stopped: it emits the value at the current beat once on each transport change, then stays still.
- The pure function lives in `plugins/lfo/src/wave.ts` and is unit-tested.

### 6. Control sliders (`com.ivandaw.control-sliders`)

A `modulator` with two sliders, each driving its own output.

| Field | Value |
| --- | --- |
| kind | `modulator` |
| ports | `a`: modulation, out; `b`: modulation, out |
| parameters | `a`, `b`: float 0..1, default 0.5, automatable |

- The sliders are the generic node-panel strip; no plugin UI.
- Every `automation` event for `a` or `b` sets the value and re-emits it on the port of the same name at the same time, so a move is heard at once.
- On a new control cable the router asks the source for its current value (`instance.parameter(id)` for sliders, the next tick for the LFO) and sends it, so the target jumps to the slider's position on connect.

### 7. Play-only mode

`http://localhost:5173/play_only` (or `?play_only`) opens the same scene with the graph locked: you play and shape the sound, but cannot change what is connected to what.

| Allowed | Blocked |
| --- | --- |
| Play / Pause / Stop, Space | `+ Add`, Remove, Delete key |
| BPM field | Dragging nodes |
| Plugin UIs inside node boxes (Beatality's packs and controls) | Drawing or deleting audio and notes cables |
| Volume and pan of every node, and of Master | |
| Plugin parameters in the node panel, including the two sliders | |
| Drawing, re-aiming and deleting control cables only | |
| Camera pan, selecting a node | |

- `app.ts` reads the mode once at boot into a `mode` signal (`'edit' | 'play'`). Canvas and panels check it; actions do not, so tests stay simple.
- Master gets a pan: a StereoPannerNode after the master gain, driven by the `pan` field Master already has in the project. Its volume and pan show in the node panel and on its box footer, in both modes.
- Vite already serves `index.html` for unknown paths in dev (`appType: 'spa'`). `vite preview` needs the same fallback, checked in e2e.
- A small "Play only" tag sits next to the IvanDAW title.

## Repo workflow

Claude commits straight to `main` in ivan-daw and ivan-daw-core, and opens PRs only in Beatality. Each task that changes what you see or hear stops at a localhost check before the next one builds on it.

| Repo | How changes land | Before each push | Tags / releases |
| --- | --- | --- | --- |
| ivan-daw | Commit to `main`, one commit (or a few) per task | `pnpm check` green | none |
| ivan-daw-core | Commit to `main` | `pnpm check` green, `dist/` rebuilt | Claude pushes `v0.2.0` from Ivan's PC session; ivan-daw then pins it |
| Beatality | Its own Claude session, PR to `master` | its own checks | CI publishes a `daw-build-<n>` release on every push to `master`; ivan-daw pins one |

Beatality is worked on in its own session from its own design; in this project it appears only as Blocker B. Tasks that need Beatality (fetching its release, checking its UI inside the node box, the final demo scene) are marked "blocked by B" in the plan and start only after Ivan says B is cleared. All other tasks go ahead in parallel.

Localhost checkpoints: when a task is marked "check" in the plan, Claude pushes, then writes in the session exactly what to open, click and listen for, and waits for Ivan's "ok" before starting dependent tasks. Tasks that are checks-only continue without waiting.

## Testing and acceptance

v1.1 is done when the demo scene plays Beatality from a held note with audible LFO and slider control, in both edit and play-only mode, and `pnpm check` is green.

| Layer | Tool | What is tested |
| --- | --- | --- |
| Camera | Vitest | `toWorld` round trip; wheel delta modes; drag, connect and hit tests stay correct with a non-zero camera |
| Control inputs | Vitest (pure) | `findPort` for `ctl:gain`, `ctl:pan`, `ctl:param:<id>`; non-automatable parameter refused; replace on a taken control input; cycle through a control edge refused |
| Router | Vitest + fake audio | `ctl:param` → `automation` with `source: 'binding'`; `ctl:gain` → ramp to 0..1.5; cable removal restores the stored value |
| Plugin UI in box | Vitest + fake plugin | `mount` once on ready, `unmount` before removal; box size from `manifest.ui`; footer volume / pan call the actions |
| Note hold | Vitest | One note on per play, one note off per stop / pause / CC 123 / dispose; none on BPM change; note change swaps pitch at the event time |
| LFO | Vitest | `wave(0) = 0`, `wave(2) = 1`, period 4 beats; phase continuous across a BPM change; still while stopped; event times strictly increasing |
| Control sliders | Vitest | Automation on `a` re-emitted on port `a` at the same time; `b` untouched |
| Play-only | Vitest + Playwright | Mode read from `/play_only` and `?play_only`; no Add / Remove; node drag and audio / notes cable draw do nothing; control cables, BPM, volume, pan, Master pan still work |
| Beatality fetch | Vitest | Picks the pinned release, skips when present, clear error when offline |
| Whole app | Playwright | Demo loads, all nodes `ready`; Play → `rms() > 0.01` within 1.5 s; Stop → `rms() < 0.001` within 0.5 s |

Listening checks for Ivan:

- [ ] Right-drag and two-finger scroll move the whole graph; cables stay attached.
- [ ] Beatality's own UI shows inside its box; dragging its header moves it; picking a pack works; volume and pan on the box work.
- [ ] Play: Beatality loops; Stop: it stops cleanly with no hanging sound. Changing Note hold's note keeps it playing.
- [ ] Draw LFO → Beatality Pan: it pans once per bar and speeds up when BPM rises.
- [ ] Draw slider A → Beatality Volume: the slider changes the level.
- [ ] `/play_only`: Play, BPM, volume and pan (Master too), control cables and Beatality's UI work; nothing can be added, moved or deleted, and audio / notes cables cannot change.

## Risks

| Risk | Effect | Mitigation |
| --- | --- | --- |
| Beatality CI needs emscripten in GitHub Actions | Blocker B takes longer | Owned by the Beatality session; IvanDAW work goes on in parallel |
| Beatality ignores event `time` (applies on arrival) | Gate opens up to 100 ms early; control lands up to 25 ms off | Acceptable for v1.1 |
| Hidden absolute URLs or global CSS in Beatality | Fails or bleeds only inside the DAW | Covered in the Beatality design; Playwright loads the real release |
| A 746 px plugin UI inside a node box | Takes much of the screen | Camera pan; zoom later |
| Plugin UI and canvas gestures overlap | Wheel or right-click fights | Only the header drags; right-drag pans everywhere; wheel over the UI goes to the plugin |
| About 40 Beatality parameters in the `ctl` picker | Long list | Group by `group`, Volume and Pan first |
| Release download on install | Offline first install fails | The unpacked release is kept; the error says how to retry |

## Decisions (2026-11-13)

- Play-only: graph locked; plugin contents, Play, BPM, every volume and pan (Master too) stay usable. Control cables may be drawn, re-aimed and deleted; no other cable edits.
- Beatality is shown as itself inside its node box, draggable, with volume and pan, cabled like any instrument.
- Beatality builds itself in CI on every push to `master`; ivan-daw pins one release; `pnpm beatality:update` moves the pin.
- Note hold plays any note (default C1).
- The demo opens with no control cables; the user connects them.
- The LFO follows the transport and BPM (one cycle per bar).
